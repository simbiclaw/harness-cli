📜 在此分支中变更的关键 Harness 规则

🔴 提交权限：只有 Arbiter 提交。P、E、V 从不提交。
每个里程碑两次提交——RED（仅测试）→ GREEN（实现 + 判决 + 翻转）。由 Hook Guard 6 + test_commit_authority.py + test_commit_model.py 强制执行。
🟣 三个持久化代理：P、E、V 在整个 ExecPlan 期间保持常驻。
没有持久化，V→P→E 反馈弧就会断裂。由 Hook Guard 2.5 + test_pev_agent_persistence.py 强制执行。V 在每次分派时接收清洁的上下文（无之前的判决）。
🟢 闭环：在 M(N) CONFIRMED 之前，不得推进 M(N+1)。
一次最多只能有一个里程碑处于活跃状态。由 test_pev_loop_closure.py + test_pev_feedback_consumption.py 强制执行。迭代上限：通过 3 次。
🔵 每个里程碑的行为性 + 结构性覆盖。
每个里程碑都必须有一个验收测试。如果没有（纯约定变更），则需要显式声明豁免。由 test_milestone_constraints.py 强制执行。区分基于目的，而非目录。
🟡 PEV 环与论文 §3.4 对齐。
四个组成部分已命名：合约形成、沙箱执行、权限化状态转换、确定性传感器。我们的扩展：对抗性验证（子代理 B）超越了纯确定性传感器。
🟠 令牌追踪 + 晋升规则 + 转向截止时间 + 边缘情况描述。
每个里程碑每个阶段消耗的令牌。≥2 次违规 → 自动晋升。截止日期已过期 → 结构测试失败。判决必须描述边缘情况，而不仅仅是计数。

Q1: 在 9006 的执行过程中，为什么 M1 需要 3 次 PEV 迭代？
✅ 正确。V 在两次连续迭代中发现了 6 个缺陷：弃用断言不匹配、空白解析、awk 管道失败在实际计划文件上崩溃，以及静默接受非数字里程碑值。所有问题都通过 V→P→E 反馈弧进行了修复。
❌ 错误。见上文。
Q2: 谁提交代码到仓库？
✅ 正确。提交权限规则是："只有 Arbiter 提交。P、E、V 从不提交。" 这由 Hook Guard 6 强制执行。
❌ 错误。见上文。
Q3: V（验证者）为什么在一次里程碑的验证中必须接收干净的上下文？
✅ 正确。在 9006 的执行中，M2-M7 全部在首次迭代中通过。分析发现 V 的持久化上下文在连续确认后积累了确认偏差。新的规则是："每次里程碑验证分派仅接收：SHA、测试名称、里程碑规范。不接收之前的判决、历史或计数。"
❌ 错误。见上文。
Q4: 什么是 "确定性传感器"（论文 §3.4.4），它们与对抗性验证有什么不同？
✅ 正确。这两个层级形成了验证底线（确定性）和上限（对抗性）。论文的模型仅描述了传感器的部分；该仓库增加了对抗性层级。
❌ 错误。见上文。
Q5: 为什么移除了 harness 分支基础设施（Guard 5、post-commit）？
✅ 正确。Guard 5 阻止了在 harness 分支上的直接提交，post-commit 钩子自动将 harness 提交挑选到该分支，而该分支在该仓库中从未存在过。该基础设施是为一个仅使用了一次的双仓库模型构建的。
❌ 错误。见上文。
Q6: 每个里程碑都必须具备什么？
✅ 正确。在 M0 交付时零行为性测试之后，test_milestone_constraints.py 现在要求每个里程碑都必须有一个验收测试或一个显式的 'Behavioral Test: none — 理由' 声明。
