Architecture · Blast radius: 最大 Question 1 of 5

9002 runtime pipeline 如何读取和消费 _rubric/ 目录下的编译产物？

编译器输出 _rubric/ 的结构是由消费者决定的。如果 runtime 按维度一次性加载整个 rules_criteria/ 目录，输出结构就按维度组织。如果 runtime 是按 item_id 逐个查找 trigger，输出就需要按 item_id 做索引。如果不清楚消费方式，重构目录结构是盲目的。

A. 按维度批量加载 runtime 启动时加载整个规则表（如 "Procedural Accuracy" 下的所有 node），一次 parse，内存常驻。编译器输出按 dimension/ 分目录。
B. 按 item_id 逐条查找 runtime 在处理某个 item 时才通过 node_id 查找对应的 rule。编译器输出需要按 item_id 做索引，或保持 flat list。
C. runtime 目前不读 _rubric/ 目录 9002 还没有实现 — 它的 KB context builder (kb_context_builder.py) 读的是 config/rubric_items.py 中的旧 RubricItem，不是编译器的 AuthoredNode。消费者尚未存在。
Architecture · Blast radius: 大 Question 2 of 5

evidence/ 下的 acoustic indicators 和 phrase lexicons 应该是什么数据形态？

Patch 1 说它们"不是独立规则"，但没说具体是什么。如果它们是 AuthoredNode（有 trigger/agreement 等全套字段），它们就能被 runtime 统一处理但引入了冗余。如果它们是纯数据（只有 threshold 值、词表），runtime 需要两个不同的加载路径。这决定了 types/compiler.py 是否需要新类型。

A. 简化为纯数据 (dict / list) acoustic → {indicator_name: {threshold, unit, description}} 的 YAML；phrase → {group_name: [word_list]} 的 YAML。不继承 AuthoredNode。runtime 需要单独的 evidence loader。
B. 保持 AuthoredNode，但字段精简 去掉 agreement、applicability_gate、hard_fail_rule 等不适用字段。保留 trigger (存阈值) 和 corroborators。runtime 可以复用 rules_criteria loader。
C. 内联到 rules_criteria 节点中，不独立存储 需要声学证据的 item 的 trigger.spec 直接写具体的阈值（如 "speaking_rate ∈ [120,220] wpm"），需要词表的写具体词表。不产生 evidence/ 目录。
Data Model · Blast radius: 中 Question 3 of 5

hard_fail_rule (B-C 产物) 应该存在哪里？

当前实现把 hard_fail_rule 附着在单个 rules_criteria node 上（且只给每个维度的第一个 node 设置）。Patch 1 要求分离到 gates/ 目录。但 gates/ 是一个维度一个文件，还是合并到一个文件？运行时是否需要独立查询 gate rules？

A. gates/ 按维度分文件，与 rules_criteria 严格分离 gates/procedural_accuracy.yaml, gates/empathy_and_tone.yaml... 每个文件包含该维度的 hard_fail_rule。不附着在任何 node 上。运行时做路由决策时独立加载。
B. 保留在当前结构：附着在 rules_criteria node 上 当前实现方式。不创建 gates/ 目录。hard_fail_rule 作为 node 的可选字段，运行时处理 node 时顺带检查。简单，但与 Patch 1 的层级关系冲突。
C. gates/ 合并为单个文件 + rules_criteria 也保留副本 gates/ 作为索引方便批量查询；同时 rules_criteria node 也保留 hard_fail_rule 引用（通过 node_id 反向查 gates/）。冗余但方便两种消费模式。
Data Model · Blast radius: 中 Question 4 of 5

rules_criteria 节点如何引用 evidence sources —— 通过路径、node_id、还是内联？

这决定了节点是自包含的（内联，运行时不需要额外加载）还是引用式的（通过引用链接，evidence 独立加载和缓存）。内联简单但有数据重复；引用灵活但引入了解析依赖。

A. 内联：trigger.spec 直接写阈值 "speaking_rate ∈ [120, 220] wpm AND intensity_std < 15 dB"。节点自包含，不依赖外部 evidence 文件。evidence/ 目录存在但仅作为人类可读的文档参考。
B. 引用：corroborators[] 存放 evidence node_id corroborators: [{name: "speaking_rate", independence_class: "independent", ref: "evidence/acoustic/indicators#speaking_rate"}]。运行时需要按 ref 去加载对应的 evidence 条目。可共享，无重复。
C. 混合：内联核心阈值 + 引用详细指标 trigger.spec 内联最关键的 1-2 个阈值，corroborators[] 引用剩余的 evidence 指标。兼顾运行时效率和完整性。
Workflow · Blast radius: 小 Question 5 of 5

evidence 和 gate 节点的编译，应该在 compile_rubric() 内部完成，还是独立调用？

当前 A2-ac / A2-ph / B-C 都是独立函数，不在 compile_rubric() 的 per-item 循环中。Patch 1 要求 compile_rubric() 产出完整的 CompileResult（包含所有三个产物品类）。这决定了函数签名和测试策略。

A. compile_rubric() 内部完成全部编译 per-item 循环后调用 acoustic/phrase/gate 编译器，一次性产出 CompileResult。一次调用 = 完整输出。函数签名变大。
B. 保持独立调用，由上层 orchestration (CompilerIO / CLI) 组装 compile_rubric() 只处理 per-item 编译。acoustic/phrase/gate 由调用方分别调用后合并。保持纯函数单一职责。
